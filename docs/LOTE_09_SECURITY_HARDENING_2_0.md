# LOTE 09 — Security Hardening 2.0

## Status

Security hardening completed without changing application UI or offline/PWA behavior.

## 9.1 CSP decision

The current Next.js application uses inline scripts/styles generated by the framework and by the existing PWA/runtime path.

A direct replacement of `script-src 'unsafe-inline'` with a nonce/hash CSP was **not** performed in this lot because doing so safely requires request-time nonce propagation and validation across the Next.js document/runtime. That can change rendering/caching characteristics and can break the PWA if implemented only at the header level.

The enforced CSP was nevertheless tightened with:
- `frame-src 'none'`;
- `media-src 'self'`;
- existing `object-src 'none'`;
- existing `frame-ancestors 'none'`;
- exact Supabase `connect-src`;
- `worker-src 'self' blob:`;
- `manifest-src 'self'`.

A future CSP nonce migration should be a dedicated, tested change, not a blind string replacement.

## 9.2 Auth

Client-side authentication already delegates session handling to Supabase Auth.

This lot does not attempt to implement a client-side brute-force limiter, because that is not an effective security boundary.

The destructive account-deletion Edge Function now has:
- best-effort per-instance rate limiting;
- strict production origin fallback;
- authorization validation;
- bounded authorization-header length;
- bounded request body size;
- generic server-side deletion errors;
- no token/user ID/error-message logging.

Session expiry, refresh-token rotation, password policies and MFA are controlled by Supabase Auth configuration and should remain configured there. MFA is documented as a future capability rather than simulated in the client.

## 9.3 Edge Functions

`delete-account` is currently the only Edge Function in the repository.

It now applies:
- method validation;
- CORS/origin validation;
- request-size validation;
- rate limiting;
- Bearer token validation;
- server-side identity derivation;
- generic error responses;
- no sensitive logging;
- `Cache-Control: no-store`.

The rate limiter is intentionally best-effort and in-memory. It is not presented as a distributed security control.

## 9.4 Client storage

The application currently uses `localStorage` deliberately for offline/PWA persistence and synchronization.

Moving the financial application state wholesale to IndexedDB plus Web Crypto would add key-management and migration complexity without materially protecting against XSS: code executing in the origin can generally access the decryption capability.

Therefore this lot **does not perform a blind localStorage → IndexedDB migration**.

The existing storage layer remains scoped by authenticated user and the application already clears local representations during account deletion.

## Operational conclusion

No visual UI changes are introduced by this lot.

The security posture is improved primarily at the network/Edge Function boundary while preserving:
- offline operation;
- PWA behavior;
- current Supabase session flow;
- existing application storage semantics.

## Future hardening candidates

1. Dedicated CSP nonce/hash migration with production/PWA regression testing.
2. Supabase Auth MFA when the product requires it.
3. A distributed rate-limit mechanism if additional Edge Functions become security-sensitive.
4. IndexedDB migration only if a concrete threat model demonstrates a meaningful benefit.
